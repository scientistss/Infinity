# 地形改造器：独立增量规格草案

状态：仅规格，尚未实现、验收或发布。先完成手动运输装载版本，再在其通过验证的准确基线上实施本增量；运输候选的验证结果不能替代本增量验证。

本规格的代码核对基准是 `f96894eb1b32737ab403890ed83fdb3da41a0644`（0.6.15-alpha.1 / v9/r9），其经济核心继承 `5332526`。文档基座为 `02ae2934525295558bbd43c381a8d8fd52b3bc5b`。以下分别标明已有定义、确定的兼容原则和待审定的新增规则，不能把建议当作历史约定。

## 1. 范围与不变量

一期只开放 `terraformer` 的可见、可付款、完成扩格及完整持久化闭环。保留 `CURRENT_PHASE = 3`，使用单一建筑可用性判定显式开放地形改造器，供列表、队列、协议、计划提示及模板共同引用。不得为了显示它整体开放 P4/P5/P6；太空船坞、月球设施、联盟仓库等仍按原规则关闭。

已确定的兼容原则：

- 旧星球 `fieldsMax`、旧地形改造器等级、钱包、已付队列及其来源原样保留；迁移时新增授予账为零。不得用旧等级乘 5 追溯补格，不得按生成器重新计算旧星球上限。
- 新版正常逐级升级只有真实完成时才增加总格子5；该级占1格，所以可用格净增4。旧已完成等级不追溯补格；旧已付项目按第4节另行选定的新增兼容规则A处理，保持旧完成收益、不扩格。不得将这项政策假称“不追溯”的必然推论。报价、创建计划、保存模板、入队、等待、取消和读档本身均不授格。
- 维持现有满格规则：`usedFields + buildQueue.length >= fieldsMax` 就不能入队，包括地形改造器。不能以未来会扩格为理由，提前给予满格豁免。
- 本增量不调整其他生产、价格、时长、曲率效果、钱包运算、计划预算、付款归属或离线时限，不增加拆除、月球或持续供给玩法。
- 格子仍为有限整数，`fieldsMax <= 10000`；超出时拒绝新增付费，不截断奖励，不先收费再少给格子。

### 不能忽略的 r9 事实

`save.readPlanet/readOrder` 接受完整建筑目录：旧 r9 可以有非零地形改造器，也可以有 manual、protocol 或 plan 的已付地形改造器队列。其付款身份、计划凭证仍须通过现有交叉验证，但 reader 没有用 phase 拒绝隐藏建筑，也没有要求所有普通建筑队列目标连续，或已用格不超过上限。

此外，旧 `readOrder` 会把 `remainingSeconds` 收缩到 `totalSeconds`，旧 reader 也接受部分缺省值和金额表示的规范化。必须区分原生序列化档、旧 reader 已支持的规范化输入，以及新版额外造成的字段损失。原始输入一律逐字节保护；不能宣称每个旧 reader 接受的手工 JSON 都曾被逐字段原样保存，也不能用新增通用拒绝条件抹掉旧兼容范围。

## 3. 待审定的能源规则 E

以下为本增量拟定规则，尚非历史原文完整约定或已实现规则。经当前代码与公开文档核对，未发现与已有明确规则冲突：

1. 对目标等级 L，能源门槛采用 `floor(1000 × 2^(L−1))`，不应用成本缓和；三种资源价格继续完全使用现有 `costFor`。这延续同表基础因子及研究能源先例，但建筑能源折扣的历史意图仍待审定。
2. 在实际入队、扣除三种资源之前的同一即时状态，检查付款/执行星球 `economy(local).supply >= requiredEnergy`。等于门槛可入队；不足时为非资源阻塞，`onlyResources` 必须为 false/缺省，不能触发补给运输解决“缺电”。不扣能源、不改变矿场需求，也不占用可消费的“能源余额”。
3. 仅在入队前检查，之后因调低电站、核聚变断燃料或其他变化导致供能下降，不暂停、取消或额外收费。本次付款恰好把重氢扣到0、进而使核聚变实际供能下降，也不在扣款后补审或回滚已经合法付款的项目。已付旧队列不追加前置或能源复审。若希望开工或完工再次检查，将成为另一规则，必须另行明确，不得隐式引入。
4. 排队第二级时按其真实目标等级检查能源，不能一直显示/检查一级 1000。当前/目标能源均须为可表示的有限值，否则原子拒绝；地形改造器目标仍不超过既有存档等级安全上限 1000。
5. 所有实际付款入口执行同一校验。计划和模板可保留尚未满足条件的意图，但显示当前阻塞，逐次付款时重新检查；创建意图不是通过能源验收，也不是付款。

若 E 获准，独立数值例为：未解锁成本缓和时一级 C=50000/D=100000/E=1000，二级 C=100000/D=200000/E=2000；解锁后一级不变，二级 C=99500/D=199000/E=2000。能源数值不进入资源账、运输货物或退款。

## 4. 已选定的新增兼容规则A与r10方案M（尚未实现）

### 选定A；保留B作为收益政策对照

两方案均保留旧原件、fieldsMax、已完成等级、三种资源paid、钱包、jobId/taskId/source及计时；迁移时授予计数为0，不补已完成历史等级，不追加能源检查或重新付款。差别只在迁移后旧已付工作的未来真实完成收益。本增量已选定A，B仅作未采用方案分析：

- **A（已选定）：旧paid保持旧完成收益。** 旧 `completeActive` 只用 `Math.max(当前等级,targetLevel)` 更新等级，不扩格。A延续它，旧paid未来完成也不授格；新版新付款工作才在正常逐级完成时+5。这有利于保留旧实现的结果，且不使接近10000的旧工作因新增收益阻塞；但会使两份完全相同升级因付款时间不同得到不同收益，并与已有“每级+5格”描述带来的合理期待发生落差。它是明确选定的新增兼容政策，不能从“不追溯旧等级”自动推导，必须在迁移说明与旧队列中展示。
- **B（未采用）：旧paid在新版未来真实升级完成也+5。** 迁移不先发奖励；原付费job将来被实际完成并消耗，且完成前后地形等级确实上升时，才给一次5格。普通连续目标无需改钱、ID或计时，完成前后快照及队列移除可以保证不重复，原则上不需要以付款时间剥夺资格。重复/跳级旧目标与10000边界需要下述额外明确规则，不能偷改为A或静默截断。

选择A是保留旧付费工作既有完成结果的独立政策决定，并不表示B技术上不可实现。A的实施边界是：所有旧paid terra保留原target、paid、time、job、source和计划/运输回执及旧完成收益；新版新付款入队的真实逐级升级完成才+5。迁移不授格，不追加旧队列能源检查，不为此拒绝可按原规则读取的旧档。

### 已选jobId floor与同星旧terra隔离分别解决什么

**floor只记录付款规则边界。** 选定A保存迁移时 `orders.nextJobId` 为 `terraformerGrantJobFloor`，如上例为42：41属于旧paid、42及以后为新版paid。它不分配ID、不改旧job、不等同完成水位，不能单独防止重复授格；同一新job若被错误重复完成，floor两次都会通过。若选择B，floor不是发奖资格门槛；只有当需要区分旧非连续目标与新版严格逐级目标时才考虑保留一个明确命名的兼容边界，不能仍把它解释成旧job禁领。

**混排检查解决目标序列，不解决收益资格。** 当前 `nextTargetLevel = 已完成等级 + 同建筑队列项数 + 1` 隐含队列连续。例如等级2、旧队列仅目标5时，新入队会报价目标4；旧5先完成后，新4不再升一级。又如等级2、旧目标3/3时，新增目标5跳过4。这些是旧reader允许而当前普通入队假设不能正确推导的状态。floor无法修正目标。

等级2、旧目标3、新目标4的正常混排本可定义正确完成，因此全面暂缓不是数学上唯一的防重复办法。本增量另已明确选择较小实现面的兼容隔离：仅该星球仍有旧paid terra时，暂缓该星新terra付款，保持旧项目按原规则运行或由玩家明确取消；其他建筑、其他星球不受影响。无论旧目标连续与否均采用同一可见规则，旧队列清空后再按当前真实等级报价。不得据此拒绝源档、暗改 `nextTargetLevel`、重报已有费用或替玩家取消。

### 选定A的最小r10元数据与未采用B的差别

选定每星球新增严格必需 `terraformerFields: { base, grantedLevels }`：迁移base取当时旧fieldsMax、grantedLevels=0；新星球base取其实际初始格子。保留 `fieldsMax = base + 5 × grantedLevels <= 10000`；base为1–10000整数，grantedLevels为非负安全整数。若B只给每个真实升等job一次+5，则仍可检查grantedLevels不大于已完成地形等级，但旧跳级时不能反推“每一等级均授过格”。

- A使用floor：其为1到当前nextJobId的安全整数，旧job原样不补字段。令G=所有星球grantedLevels之和，P=当前全部已付建筑/研究/造船队列中jobId≥floor的唯一ID数，I=nextJobId−floor；必须验证 `G + P <= I`，并保留现有全帝国付费ID唯一性。造船批次即使部分完成也只按其唯一jobId算1，不能按数量重复计数。该界把已经授格和仍在付的占用共同约束在真实已发行ID空间内；它是必要的一致性条件，仍须配合真实job原子消费和逐项完成验证，不能单独证明任意手改历史。普通连续旧队列不能仅因ID低于floor而被当作异常。
- B不能使用A的计数上界：上例旧job41完成后授予1，而nextJobId−floor=0。最小计数上界可继续依赖已有全帝国job发行空间 `nextJobId − 1`，配合真实job消费、前后等级、每星base/计数/fields等式；若要更紧的“迁移旧可授格项数”证明，需要另存有界旧资格集合/数量，不能免费推断。只有选择了B的重复/跳级收益定义，才能定最终校验。
- 两方案都不把内存标记当持久化授格账；不为此发放第二套付款ID，不新增无限完成历史。现有真实队列+已付凭证、原子完成并移除job、持久化授予计数共同承担不重复保证。任意手改JSON的历史真实性不在结构校验能证明的范围内。
- 显式逐job授格资格作为未采用的表示方案保留对照；当前选定全局floor，不再添加第二套资格来源。B若今后另行采用，也不能把旧字段缺省当0取消收益，须另开变更合同。

### 玩家可见提示（A为本版合同；B仅保留对照文案）

- A迁移/旧队列必须明确：`旧版已付：完成升级，不增加格数。` 并补充原费用/剩余时间保留；新版说明：`本版新付款入队每级+5总格、建筑本身占1格。` 不能只写“兼容迁移成功”隐藏收益差别，也不能诱导玩家必须取消重付。
- A同星隔离：`该星球仍有旧版已付地形改造器，先完成或明确取消旧项目后，才能按新规则付款升级。原队列继续，其他建筑和星球不受影响。` 必须展示原因；不能把整个旧存档或整个建筑系统标为不可用。
- B正常旧队列：`旧版已付款项目已保留，不再扣款；本次真实升级完成后增加5格。当前尚未扩格。`
- 重复目标：`此项目标等级已由前项覆盖；原付款和队列保留，完成不会再次升级或扩格。` 若取消需显式操作，退款照实际paid与现行规则。
- 非连续目标阻止新增：`现有旧队列目标与当前等级不连续，暂不能确定下一次正常升级。旧项目保持原样，请先完成或明确取消后再新建。`
- B硬上限冲突：`旧已付地形项目完成应增加5格，但会超过10000格上限。原存档已保留，尚未扣费、截断奖励或改写原队列；此兼容情况暂不能自动推进。` 仅在确实保护/停止且其范围已说明时使用；不得假称其他正常星球或旧档同样不兼容。

### 迁移与拒绝合同

1. 先验证 lineage/version/revision，再按该历史修订的既有兼容规则读取；r9 到 r10 只增加上述元数据。对固定旧源码原生导出的规范档，旧字段、标量类型、数组顺序及封套 `savedAt/lastTickAt` 保持。对旧 reader 允许的非规范输入，以同一固定旧 reader 的规范化输出作历史语义基线，并独立保存原始字节；新迁移剥离新增字段后须与该基线一致。不得把新 reader 自己的输出当历史 oracle。迁移不运行授格或新增经济变化，新字段从读取后的明确边界生成，不从等级补奖励。
2. 同源 r2–r8 继续各自历史迁移链，走到 r9 历史形状后才追加 r10 字段。禁止把所有“revision != 10”都当成缺少 r9 模板：真实 r9 已有建筑模板，必须完整保留。
3. 用固定历史源码的实际 serializer 导出原生 r9，至少包含非零地形等级、manual/protocol/plan 旧地形付费、其他建筑、共享研究、造船、运输、模板和编成；先经相同历史 reader 接受，再验证 r10。不可只在新档上改 revision 充当旧输入。此类专门合成的兼容样本应明确标为合成，不能当自然玩家成长证据。
4. 接受原生 r9 中非零地形等级及可无损迁移的已付地形队列，禁止笼统声称旧地形必为零。不得为了套用新规则重算旧 paid/time、换 ID、清队列或改 target。
5. 对旧 reader 已有的规范化，列出允许差异并由固定历史 reader 证实，不新增全档通用拒绝。例如 remaining>total 不能伪称从未被旧 reader 接受；如沿用其原有收缩行为，应明确记为历史规范化用例，保留原字节，并证明新版没有进一步改变时间。原生已付队列不得为适配新规则重算、clamp、换ID或修复费用。若出现超出历史基线的变化，或精确账/队列无法保持旧语义，则整档保护性拒绝，报告具体字段与原因；不部分迁移星球、不伪造回执。
6. 对旧 revision 夹带本版新授格元数据，包括深层嵌套、空值或伪造floor，按现有加法迁移防夹带模式拒绝。r10 缺字段、未知子字段、越界、等式不符、重复身份、错付款星球或过期 counter 一律拒绝，不能默认为零。
7. r10同一星球若同时有jobId<floor的旧terra与jobId≥floor的新terra，必须拒绝，因为选定隔离规则不可能合法产生这种混排；纯新版terra队列目标必须从当前等级+1逐项连续。r9迁移时所有原paid均属于旧侧，所以不据此拒绝旧异常目标。纯旧terra的重复/跳级/低于已建目标继续按旧reader合法范围保留。不给旧数据强加全局 `usedFields <= fieldsMax` 或普通队列目标连续的新条件。新版新付费地形队列须确定为真实下一等级；旧队列按已选A收益及原目标语义走明确兼容支路，不能仅因不满足新队列规则就拒绝迁移。若某个后续取消操作会产生非法目标或无法精确守恒，拒绝该操作并保留整个原状态，不替玩家修改队列。明确回归例：旧地形0、两个旧target=1，取消前项会使后项target=0；必须在候选事务中原子拒绝，钱包、paid、目标、身份、计时、计划流水及授格账全部保持，不能先退前项再失败。取消后项仍按其真实合法条件独立判断。
8. 原生启动升级仍先保留/读回核验原件，再提交/读回新档，成功后采用离线结果。备份失败、配额不足、写后读回失败或跨标签冲突时冻结，不展示未持久化的额外格子；保护导出返回原始完整字节。
9. 旧 r9 reader 必须拒绝真实 r10；新 reader 仍拒绝 v8、原版 r1 和已知另一谱系 `0.7.0-alpha.3` v9/r6，不凭相同 schema/版本名放宽保护。保持独立 storage key，不碰另一谱系原存档。
10. r10 中授格账或floor丢失、损坏不能按旧档重建、回填为0或重置初始值，否则会丢掉奖励资格边界。启动进入保护并导出原件；只接受有效完整替换或明确新局。导入旧快照是替换整个世界，不合并当前授格计数；不得承诺恢复从未成功保存的状态。
11. `Number.MAX_SAFE_INTEGER` 是现有ID耗尽哨兵，不得分配为新job；floor可等于该哨兵，此时无新授格工作可付款；既有旧paid按A完成且不授格，已有新版paid照其资格完成，不因ID耗尽重新发ID。失败不扣款、不动预算/队列/授格账，不为解锁功能循环使用旧ID。

## 5. 完成与格子边界合同

- 在真实事件边界，合格地形job必须是该星球实际已付队首，属于当前世界，计时已真正到达完成点。新版新付费job目标应为当前地形等级+1；旧job保留原Math.max语义及旧完成收益，按A不扩格。不能用重复目标的幂等等级写入再次发奖励；资格与真实升等、job消费均须成立。
- 对正常获授一次的升级，将付款完成记账、升一级、`grantedLevels + 1`、`fieldsMax + 5`、移除job作为一次不可分割转换。旧重复/跳级job按A验收，不授格且不假称全都升一级；任一安全验证失败不得只改部分状态。普通建筑沿用原完成规则。
- 对source=plan的新版授格job，必须确认实际付款归属、activeJob及（若存在）运输currentWork凭证有效，且credit确实完成预期记账。现有 `creditPaidJob` 对某些失败会静默返回原state；不能仅调用它之后无条件升等、+格和移除job，也不能把manual路径合法的原state返回混同计划成功。验证/credit失败时整笔完成候选不提交，并给安全阻塞原因；测试须直接覆盖凭证不匹配与credit未生效。
- `logic.tick` 当前在扣除本段时间后判定到点，但传给 `completeActive` 的 head 尚可能带有扣段前 remaining。实现必须正确传递/判断到点条件，不能直接在现 helper 加 `remaining == 0` 导致合法完成全部停住，也不能让 UI/读档直接调用授格。
- 新付款前检查 `fieldsMax + 5 × (已有合格未完成地形 jobs + 本次1) <= 10000`。这只是安全上限预留，不增加当前可用格；仍按现有一 job 占一格做入队判断。completion 再防御性验证总量，绝不 clamp 到 10000 少给奖励。
- 例：9990 可为两个新地形工作预留至10000；9995只能再付一个；9996–10000不得付任何会授格的新地形工作。A中旧无授格job不占授格上限预留，但其普通建筑格预留保持；有这类job的同星新terra付款已另行暂缓。B的超限矛盾仅保留在第4节，不进入本版实现。
- 取消原项及后续重定价沿用原钱包/计划规则，不改已授格账。未完成项目无可回收奖励。取消第一项后的新版同建筑目标下降，后项只在真实完成时各授一次；不得因改 target 再额外发放。
- 反复 tick、catchUp、保存、导入/导出、重载、零时长推进和旧 UI 回调不得使同一完成再授格。载入已完成后快照无 job；载入完成前快照只重现该快照世界一次完成，不能把奖励叠加到另一当前世界。
- 升级、退款及完成只影响 job 所属星球；玩家切换 activePlanet 不转移能源检查、付款、格子或日志。导入其他世界替换而非合并格子账。
- 曲率重置与新局清除本轮星球、队列及授格账；新母星回到正常163格/地形0/授格0，既有科技、曲率、模板和计划终止规则不变。重置时在保留既有job counter的前提下，把floor设置为该counter，为新世界建立无旧付费授权的边界，G=P=0。殖民建星必须用实际生成字段初始化 base，避免 createPlanet 的母星缺省163与殖民地字段不一致。

## 6. 呈现与统一校验

建筑卡至少展示目标级、三种真实价格、现有供能/所需能源、前置、当前已用/上限、实际付费队列预留，以及“完成总格+5，该级占1，可用净+4”。队列及迁移提示必须如实显示已选A对旧已付收益和同星新付款隔离的处理，明确旧项不增加格数。未满足条件时给具体原因，不能仅显示“无变化”。

manual、protocol、普通有限计划、运输有限计划、模板生成计划共享付款门禁。只读报价/模板警告也引用共同可用性和能源规则，不能继续硬编码 phase 把已开放 terra 说成未开放。模板整批字段不足提示须说明按当前格子判断、后续实际扩格后重检，不能提前把预计扩格当可用格，更不能保证整批一定完成。

能源由生产设置、核聚变燃料和卫星变化而变；任何缓存/快照必须能更新能源提示，实际提交再取当前数据。能源不是长期授权金额，无需为了每帧变化重建完整累计报价。旧确认控件在星球变化、世界替换、曲率重置、保护模式或自身节点失效后不能恢复付款权限；既有固定付款星球的有效计划不随页面选择变化。

## 7. 独立验收合同

下列是新增实现后的必须项，目前不宣称已经执行；第4节另列的8项旧reader合成证据不替代这些门禁。不得以存在测试脚本、单元数量或运输版本绿色代替本项结果。

### A. 数值与领域

- 独立断言一级/二级成本、能源曲线、成本缓和及建造时间；expected 值不调用待测公式生成。保留旧生产和自然成长 golden，按相同初始状态比较非 terra 行为。
- 前置分别缺失、只在队列中、恰好满足；供给在门槛下/等于/上方；supply 足够但 supply−demand 不够；不同产量设置、卫星、重氢耗尽与实际核聚变降额；入队后供能降低；本次付款扣尽重氢导致聚变降额时仍按付款前即时供能接受、不二次审查；排队下一级能源递增。
- 四类入口及运输计划共用能源/满格/上限门禁；缺能源不是 onlyResources，不产生补给航班；失败不扣钱包、不占预算、不发 jobId、不授格。模板仅建意图，不立即付款或授格。
- 空闲队列、等候队列、最后一个空格、满格、两次连续升级、取消头/尾、取消后降级/精确退款、预算不足、暂停计划已有付费仍完成；每笔实际付款、jobId、taskId、source 和净占用账完整对应。
- 9990/9995/9996/10000边界、在付奖励上限预留、非法/非有限输入、目标1000边界；拒绝时整个候选不变。
- 完成前/正好完成/完成后、长tick对分段tick、同一tick两颗星球完成、切换activePlanet、零tick、离线cap内/外；完成次数与真实格子增量逐项对应。

### B. 旧档与持久化

- 固定历史 r9 原生档：地形0与非零、非默认fieldsMax、各来源旧已付队列、已开始和等待计时、计划/运输回执。迁移前后剥离新增字段后逐字段相等，新授格账必为0。
- 非零旧等级在迁移、load、catchUp初始化时不追溯补格；旧已付工作完成按审定M规则处理；其后新付款完成恰加5。旧取消返还实际paid，既有来源、计数器和流水守恒。
- r10同星旧新terra混排拒绝、纯新目标断级/重复拒绝、纯旧异常目标仍合法；旧重复target=1取消首项会降出target0的原子拒绝；新版plan凭证缺失/错owner/错credit状态不得授格或部分移除。G+P=I与G+P>I边界同时覆盖建筑、共享研究及部分完成造船批次。
- 原 r9 可接受但会被规范化的 remaining>total/缺省值/金额表示样本，分别保存原字节和固定旧reader输出，与新迁移投影比较；旧非连续/重复目标标注实际旧语义，不能新增一般拒绝。仅新版额外损失或无法守恒时完整保护，不偷改输入以让用例通过。
- 新授格账/身份损坏、夹带r10字段、伪装旧revision、错planet、重复job、counter过期、缺字段、篡改base/granted等式、G+全部队列中合格唯一paid-ID数P超过I、已完成job重放全部拒绝或无副作用，不产生奖励。ID最后一个可发值、哨兵耗尽、floor等于nextJobId均有明确用例，覆盖A旧paid完成后G仍为0；r10丢账不得伪装旧档重新初始化。
- 连续导出/导入/重载、已完成后多次catchUp不重复；r2–r8链、已有r9模板/编成保留；旧r9 reader拒绝新r10；异谱系和旧版本仍保护。
- 原生HTTP、localStorage及File.text覆盖自动启动升级、手动文本/文件导入、写前备份、配额/写入/读回失败、冲突标签、冷重载恢复和保护导出。保存的升级状态、原件字节与授格终态分别核验。

### C. 真实玩家闭环

1. 从固定种子正常新号，或可追溯的既有自然成长保存点开始，使用正常收集、生产、仓库、研究、建造和必要运输取得纳米1、能源科技12、真实供能及付款资源。不得注入资源、科技、格子、已完成计数，或修改时间/倍率来伪称自然成长。
2. 通过真实建筑页看到地形改造器和当前门槛；正常入队，逐笔验证资源实际扣除、已付job身份及格子尚未增加；保存并原生重载在付项目。
3. 真实倒计时完成一次：等级+1、总格+5、已用格+1、可用格净+4；日志、概览、建筑页及扩张查看显示同一星球结果。再次保存/冷重载仍只加一次。
4. 在新释放空间内正常完成另一项建筑，再用有限计划或模板执行下一次地形升级；在付款前能源不足则等待，提高真实供能后付款，取消一次实际在付地形项目，验证精确退款且无授格，再明确重建并完成。
5. 在另一实际殖民地验证付款与扩格归属，同时切换选中星球；随后核对曲率预览损失，确认重置后163/0/0及既有保留项，重用模板也须重新满足本轮前置/付款，不能复活旧job或授格。
6. 另用明确标注的合成边界档测试满格、10000上限、历史兼容和存储故障。自然成长证据与合成故障证据分开。若领域自然模拟已经完成而原生UI接续尚未通过，应分别报告，不能称真人实时完整试玩。

### D. 发布门禁

独立审阅复核E和已选A/M的旧收益、同星隔离、授格计数及异常取消边界及上述不变量，再实施。候选准确提交必须完成相关单元/类型/构建、旧回归与自然路线、上述原生玩家流程和迁移保护；保留失败报告，不能改golden或放宽边界换绿色。发布以准确SHA的完整CI、构建文件哈希和实际版本核验为准，单列尚未测试的浏览器/平台及性能范围。
