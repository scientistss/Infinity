# 命名编成一次复制到历史演练

已交付版本 **0.6.23-alpha.1 / v9/r14**，精确来源为 [241a51d](https://github.com/scientistss/Infinity/commit/241a51de31364e9086abcc304884bf9df7cd6912)。完整 CI、独立推广和发布已完成；后续 0.6.24-alpha.1 继续包含本能力。原验收归档的一处同名覆盖缺陷及限定补证保留在本页末尾。

这是纯 UI 数量入口，不增加存档字段、世界状态或新的执行授权。

## 玩家合同

1. 从当前保留的侦察报告打开演练，仍从全零数量开始。
2. 显式选择当前保存的编成。选择只显示来源，不写入数量、不报价、不运行。
3. 显式点击复制，原子替换全部 13 类可飞舰船的演练输入；未列舰种写为字符串 `"0"`。历史报告、当前出发星球和速度不变。
4. 库存不足仍保留完整目标，例如目标 20、停泊 7，填入 20 并显示缺 13。不能运行超库存的编成；不截成 7、不自动补船、不把已付款待造、其他星球或在途船计作停泊库存。
5. 每次新选择及复制都清除旧演练结果及旧 Fill 资格，即使数量恰好相同，也必须再次明确 Run。
6. 数字复制后独立存在。编成以后改名、修改或删除，不会偷偷改写已复制输入或已完成示例，不形成删除引用或持续模板订阅。来源明确标为复制时的 ID、修订和名称；手动修改后标记修改或清除出处。

保存编成的每种数量上限仍为 1,000,000，最多 32 个。原演练手填上限仍为每种 1e12。沿用 r14：实际已停泊但攻击前置不足的舰船仍可运行历史示例；Fill 必须通过普通最新攻击报价，真正付费出征仍要在舰队页独立点击并重新报价。

## 最窄模型边界

`src/ui/npc-rehearsal-formation-model.ts` 仅导出数量数据和出处：

- `listNpcRehearsalFormations(entries)`：冻结的 `{ id, revision, name, index }[]`，仅供显示及控制器捕获真实对象。列表次序就是当前数组次序。
- `buildNpcRehearsalFormationCopy(entries, selected, landed)`：冻结的 `{ origin, values, rows, total, totalDeficit }`，或无效时 `null`。`origin` 只有 ID、修订和名称；`values` 为完整 13 项字符串；每行只有 `unit/target/landed/deficit`。
- `entries` 只接收现有编成列表的只读子图，绝不传整个游戏状态。`selected` 必须是当前唯一的实际对象。相同 ID、修订或值的克隆不能替代当前来源。
- `landed` 是仅含 13 种可飞舰船的数量记录，缺项视为 0。控制器从当前真实停泊库存按自有数据描述符投影；不传队列或补船计划。

验证在读取数值前检查普通或空原型、精确字段、可枚举自有数据描述符；拒绝 getter/setter、隐藏字段、symbol、未知字段、卫星、防御、稀疏/变形数组、重复 ID/来源对象/ships 别名及库存与来源 ships 的别名。对任一非法保留记录整库关闭，不悄悄跳过坏记录。保存数量采用既有规范的非空正整数稀疏记录，每种最多 1e6；不归一化、不裁剪非法输入。

所有返回对象、数组及行均 detached 且冻结，不冻结或修改调用者数据。缺额只在库存小于目标时相减，目标总数和缺额总数最多为 `13 * 1e6` 安全整数。无需新的 Decimal、经济计算、价格、队列、战斗、RNG 或定时器。

## 控制器责任

模型没有会话状态。控制器必须捕获世界 token、当前来源星球、原选择控件、实际编成对象、ships 对象和完整值签名；复制前从当前上下文重新核验。编辑、删除、同 ID 替换、相同内容对象替换都退休待复制选择。纯模型对新的数组容器仍要求实际来源对象和内容合法；界面额外保守地在 entries 数组身份变化时退休待复制选择并要求重新选择，这不会偷偷同步已复制的数字。

选择、复制、Run、Fill 遵守已有世界/保护/星球/报告/DOM 生命周期：导入、重置、曲率确认前包括取消，世界替换、来源星球变化、保护切换、报告淘汰、隐藏、取消、Back、拆卸重插都不得复活旧能力。不得从 dataset、可伪造 value 或 ID 重建能力。

复制只在可信显式操作中发生。先核验全部目的输入原节点，再消费当前选择，最后同步完整写入 13 项；不得留下延迟回调。失败复制不碰实际出征草稿。控制器负责按当前库存展示缺额，模型本身不修改 DOM。

### 原归档缺陷与精确补证

241a51d 的原归档有一份 `formation-3-save-after.json` 被后续同名场景覆盖；原封存引用与该文件最终字节不一致，不能称原归档所有引用均完好。原不可变包仍保留先前 storage 及同一路径随后一次真实手动保存的原生 storage。仅提取这两份实际 storage，按原 `beforeStorage`、`afterStorage` 键顺序及原 JSON 排版重建，所得 95567 字节的 SHA-256 为 `9d2a9cc5a11d7e1ff93e29804f941fd7ca79ade4a7855d5d52c7ea3c11bbf92c`，与原日志封存目标精确相同。

该补证不使用 expected / oracle、猜测值、时间修正或规范化；afterStorage 来自随后真实手动保存，并非重新观察更早的保存时刻。精确字节相同与独立全状态记录共同支持该项验收，但不修复或重新标记原归档，原同名覆盖缺陷仍保留。
