# NPC 轨道驻军：独立领域准备

日期：2026-10-11。本检查点在 NPC 固定生产候选之后准备下一段领域模块，尚未接入游戏运行路径。它不增加可点击的攻击任务，不改变当前存档修订，不代表战争阶段已经可玩或发布。

## 已准备的独立模块

- `src/game/npc-wallet.ts`：有限 Number 库存、共享未访问底账、按坐标的已付目标账，以及固定时间重定位。
- `src/game/npc-garrison.ts`：与星环随机流隔离的坐标驻军和永久保留的幸存数量。
- `src/game/npc-loot.ts`：每资源最多实际库存一半、按各资源可掠夺资格比例分配、总量受幸存货舱限制的整数战利品。
- `src/game/npc-transfer.ts`：NPC 专用的精确燃料付款、在途整数货物及三资源返港候选。它不改变现有普通钱包或旧任务付款规则。

现有 `GameState`、tick、舰队、存档、SaveSession 和 UI 均未引用这些模块。调用方仍须把整份候选与付款、任务身份、舰船、战报一起原子采用；纯函数本身不是执行授权。

## 明确的项目规则

这些是本项目新增设计，不是完整 OGame 规则复刻。

1. NPC 初始资源为金属 500、晶体 250、重氢 0；每秒产量为 5、2.5、1；上限为 50000、30000、10000。实际持久化的有限 Number 库存和实际采用时间是经济权威，不按理想帧频补差。
2. 普通推进只增加本地采用时钟。达到或跨过固定 H=12000 的实际采用段末时，全部库存一次结算并重定位。查询、侦察、导出和重载不主动重定位。大于等于 H 的单段足够使所有库存达到上限。
3. 同一坐标共享同一账；首次真实付费出航才保留目标记录。容量满时拒绝新增目标，已有记录仍可用。不得驱逐受损或已清空目标使其补军。首版集成已选择 512 个永久目标、60 份终端战报、64 个未终结攻击任务；本纯模块的上下文上限仍由调用方明确传入，尚未接入应用。
4. 驻军使用独立坐标盐 101：75% 为 4 轻型战斗机，其余为 8 轻型战斗机和 1 重型战斗机；NPC 战斗科技为 0。被毁数量不自动恢复。幸存者下一场仍按现有聚合战斗模型恢复完整船体和护盾。
5. 每资源资格严格为 `floor(当前库存 / 2)`，不加 epsilon。实际装船总量受幸存有效货舱限制，先按比例向下取整，再按金属、晶体、重氢顺序分配余数。没有装船的部分不从 NPC 扣除。
6. 零战利品不会重锚库存，即使该场确有驻军损失。纯库存模块不判断胜负；后续真实战斗层必须限制为获胜且有幸存舰船才取货。
7. 出航按现有口径支付一次往返燃料，抵达不再预留或扣除同笔燃料。此为现有舰队抽象，不是分段燃油模拟。
8. 新任务正值转移必须精确。燃料接口必须额外保留原始整数报价意图，不能从已经舍入的 Decimal 倒推。无法证明精确时拒绝；不得吞掉代价、少给资源或只入账部分货物。

## 数值与性能边界

- 日常推进和单目标查询对站点数为 O(1)。建账、扣款候选、严格全量读取、跨 H 重定位、序列化仍为 O(站点数)，不能据此宣称每个操作都为常数时间。
- 导入边界必须先完整验证并取得可信状态，再调用只检查头部与目标的快速路径。占位上下文是瞬时缓存，世界种子或玩家坐标改变后必须重建，不写入存档。
- 同一实际采用段序列下，额外纯查询和 JSON 重载不改变钱包。任意不同时间切分或任意额外重定位不保证未来浮点结果逐位相同。
- 已保留固定重定位的真实边界反例：D=1.799999999999636、时钟与锚均为 11999.9，连续采用 0.1、0.1 秒，固定重定位得到下一次半额资格 0，不重定位对照得到 1。规则固定执行，不用 epsilon 隐藏差异。
- 精确金额合同以可往返保存的 Decimal 十进制文本为依据。例如数学整数 1073741824000 构造后可能成为 1073741824000.0001，必须明确拒绝，不能把近似数称为原整数付款成功。
- 新转账入口只从精确的普通数据容器捕获自有可枚举字段，拒绝 getter、额外字段和继承字段，验证与转移使用同一份快照；它不替代整个存档的跨引用验证。
- 零货物返港可保留原钱包对象。已有钱包的特殊零表示与新在途货物的严格规范表示是不同入口合同。

## 已执行的局部验证

- 钱包、驻军、战利品 3 个文件：198 项定向测试通过；对应这 8 个领域文件的冻结检查点 TypeScript 检查通过；后续仍在开发的战斗模块不在本项范围内。
- 精确转移：77 项定向测试通过（原 68 项及 9 项容器边界回归）；全部 45003 个合法单资源整数货物构造与保存往返通过。
- 独立 Python 十进制方程 oracle 完成 4133922 次检查和 25 项金标；检查集合有重叠，不是同等数量的唯一游戏场景。
- 测试与金标覆盖半数相邻 Number、满仓溢出后扣款与再生产、同刻两次扣款、MIN_VALUE、同坐标共享、驻军不复生、保存往返、固定重定位差异和不可表示付款。

这些局部结果不替代实际任务集成、完整 CI、原生浏览器或可玩发布验收。

## 尚需闭合的玩家循环

侦察资源和驻军 → 合法研究与造舰 → 付费出征 → 真实最多六轮战斗及永久阵亡 → 按幸存货舱取得真实战利品 → 返回来源星球一次入账 → 同一 NPC 正常再生产并再次侦察。

集成仍需严格旧档迁移、真实到达排序、独立任务随机种子、固定战报、精确返港受阻与重试、取消/召回、离线与重载幂等、同时两批抵达、跨标签保护、容量配额和四宽原生操作验收。不能以空驻军免费取货替代这一完整循环。

## 独立准备 CI

`npc-domain-preparation.yml` 只运行于准备分支。它执行全部单元测试、构建与 8 项构建身份检查测试，并分别构建固定 `eefc0706e8bc2ce39fbfd732ab9d3b67ac190d81` 来源和候选，逐文件比较全部实际应用字节；唯一允许不同的是 `release.json` 构建身份文档。新增文件、缺少文件或任一应用字节变化都失败。原正式发布门禁没有删改。此门禁成功只能证明准备模块仍未改变执行包，不能代替攻击集成后的完整领域、迁移和原生浏览器验收；该准备产物不发布到试玩站。

## 首版总量与保存边界

64 个活攻击包括出征、战后返航、召回返航和精度受阻等待入港，直到真正终结；不能用召回或保护状态释放尚在途的名额。现有总舰队 1000 上限不变。所有在途必要战报必须保留，只有终端历史按 60 条规则裁剪。512 目标满时只拒绝新目标，对已有目标仍可出征；不得驱逐受损驻军或已取资源的账。额度与拒绝原因须在未来 UI 明示。

当前 JSON.stringify 结构预算中，特定自然小档、512 目标、60 终端报告及 64 活任务，按主档加两份同体积备份、实际键名和 64KiB 余量计算约 4618570 UTF-16 字节。它不是浏览器通用配额、实际完整新版本 reader 验收或所有旧 origin 的升级承诺；现有极限旧档自身的三副本已超过同一预算线。原始存档和全部既有备份必须保全，真实写入或迁移失败须可导出、可恢复，不能为通过容量测试清掉备份或目标状态。
